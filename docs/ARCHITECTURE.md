# Architecture

## Design goals

SecretGram provides temporary rooms in which browsers exchange encrypted messages and files while Cloudflare handles only ciphertext and routing metadata.

The design prioritizes:

- a room credential that people can read, type, and communicate without reducing cryptographic entropy;
- strict separation between routing, authentication, message encryption, and file encryption;
- deterministic single-room ordering and coordination;
- recoverable network retries without AES-GCM nonce reuse;
- logical expiration independent of best-effort physical cleanup timing;
- no third-party runtime assets or analytics.

## Trust boundaries

### Browser

The browser is trusted with:

- the room code and raw 120-bit room secret;
- derived authentication and encryption material;
- message and file plaintext;
- decrypted Blob URLs used for local previews and downloads.

Room credentials are held only in the active tab's React state. They are not written to Local Storage, IndexedDB, cookies, or server logs by the application.

### Cloudflare Worker

The Worker validates requests, enforces coarse source rate limits, routes a room locator to its Durable Object, streams encrypted file chunks to and from R2, and serves static assets. It cannot derive the room secret from the locator, verifier, or ciphertext under the stated assumptions.

### Room Durable Object

One Durable Object is addressed deterministically per room locator. It coordinates:

- room creation and expiration;
- authentication checks;
- monotonically increasing message sequence numbers;
- message idempotency and nonce-context conflict checks;
- history pages;
- versioned room-wide pinned-message state;
- one-time WebSocket tickets and hibernatable sockets;
- upload manifests and chunk state;
- maintenance alarms and room cleanup.

Durable Object SQLite stores only protocol metadata and ciphertext.

### R2

R2 stores independently authenticated encrypted file chunks under opaque keys:

```text
rooms/{room-locator}/{file-id}/{chunk-index}-{ciphertext-sha256}
```

The digest-suffixed, content-addressed attempt key prevents a losing concurrent upload from deleting or replacing the object referenced by the committed SQLite row. R2 never receives a plaintext filename, MIME type, file key, or preview.

## Room credential

A new room starts with 15 cryptographically random bytes: 120 bits of entropy generated by `crypto.getRandomValues()`.

The bytes are encoded using a Crockford-style Base32 alphabet that excludes visually ambiguous characters. Twenty-four data symbols encode all 120 random bits. A two-symbol CRC-10 checksum is appended for transcription error detection. The checksum does not replace or reduce random entropy.

The formatted code contains six groups of four data/check symbols followed by a final two-symbol group.

The invitation link puts the room code in the URL fragment. Browsers do not include fragments in HTTP requests, so the application server does not receive it. A copied URL can still leak through screenshots, clipboard history, browser extensions, endpoint telemetry, or the channel used to share it.

## Key derivation

The room secret is imported as HKDF input keying material. HKDF-SHA-256 uses a versioned salt and independent `info` labels to derive:

- `room-locator`: a 256-bit deterministic Durable Object routing identifier;
- `room-authentication`: a 256-bit bearer authentication token;
- `message-content-root`: a non-extractable HKDF root for message sending contexts.

The server stores `SHA-256(authentication token)` as the room verifier. Authentication compares the digest of a supplied token with the verifier using a timing-safe comparison.

Labels are protocol commitments. Changing them creates a new protocol version and makes existing room credentials incompatible unless migration logic is explicitly provided.

## Message encryption

A browser creates a random 128-bit sender epoch whenever it establishes a sending context. It derives an AES-256-GCM key from:

- the message root;
- the room locator;
- the sender epoch identifier;
- a versioned sender-key label.

Each sending context maintains a monotonic counter from zero through `0xffffffff`. The 96-bit GCM nonce is four zero bytes followed by the counter encoded as an unsigned 64-bit big-endian integer.

Authenticated additional data binds the protocol version, room locator, message ID, sender ID, sender epoch, and counter. The encrypted plaintext also contains the message ID and sender ID; decryption verifies that these values match the visible envelope.

The Durable Object enforces uniqueness of `(sender_epoch_id, message_counter)`. This rejects nonce-context reuse even if a buggy client attempts it.

Messages use client-generated UUIDs for idempotency:

- retrying the same ID with the exact same envelope returns the existing stored message;
- reusing an ID with different metadata or ciphertext returns a conflict;
- reusing a sender epoch/counter pair for another ID returns a conflict.

New messages also receive a random 256-bit recall capability. Its SHA-256 verifier is authenticated as part of the message envelope and retained with the ciphertext. The raw capability remains in the sending tab until the sender requests recall, at which point the Durable Object validates it and atomically replaces the ciphertext row with an ordered recall tombstone. The tombstone is broadcast to live peers and returned by history pagination, so clients remove decrypted content from their active timeline without creating a sequence gap.

Recall is a server-retention operation, not guaranteed erasure from recipients. A recipient may already have copied, downloaded, screenshotted, or otherwise retained decrypted content. Leaving or reloading the sending tab discards its in-memory recall capabilities, so that browser can no longer recall earlier messages. Messages created before recall verifiers were introduced are not recallable.

## Message pinning

A room has at most one pinned retained message. Any participant with the shared room credential
can pin a message, replace the current pin, or clear it; pinning does not authenticate the person
performing the action.

The Durable Object stores only the pinned message ID, a monotonic state version, and the update
timestamp. Clients fetch this state during initial and post-WebSocket history synchronization, then
apply versioned WebSocket updates so a delayed HTTP response cannot overwrite newer state. Pin
updates are idempotent, and an unpin request names its expected message so it cannot clear a newer
replacement pin.

Pinning never extends ciphertext retention. Recalling the pinned message or deleting it at the
retention cutoff atomically clears the pin before the change is broadcast.

This protocol does not implement a Double Ratchet, sender authentication signatures, forward secrecy, or post-compromise security.

## Message delivery

1. The client fetches all missing history pages.
2. It exchanges the room authentication token for a random, 30-second WebSocket ticket.
3. The Durable Object atomically consumes the ticket during the WebSocket upgrade.
4. After the socket opens, the client performs another history catch-up to close the fetch/connect race.
5. New messages are encrypted once, retained as pending ciphertext, and sent through the WebSocket.
6. If no acknowledgement arrives, the same envelope is retried over HTTP.
7. The Durable Object persists before broadcasting and acknowledging.
8. Reconnect uses sequence-based history catch-up and drains every page before flushing pending messages.
9. Recall events use the same ordered history and WebSocket stream, replacing message content with a tombstone on every connected client.
10. Pin state is fetched alongside catch-up and updated through versioned WebSocket frames.
11. Authenticated room metadata and WebSocket delivery frames report the remaining retained-event
    slots. A newly stored message consumes one slot, an idempotent retry does not, and recall replaces
    the existing row without consuming another slot. Retention cleanup restores slots.

Server acknowledgement means only that ciphertext was stored. It is not a recipient read or delivery receipt.

## File encryption and transfer

Every file receives:

- a random 256-bit AES-GCM key;
- a random 64-bit nonce prefix;
- a UUID file identifier;
- a fixed chunk plan.

For each chunk, the 96-bit nonce is the random prefix followed by the unsigned 32-bit chunk index. Authenticated data binds the room locator, file ID, total plaintext size, chunk size, chunk count, chunk index, and expected plaintext length.

The encrypted file descriptor—including filename, MIME type, file key, and nonce prefix—exists only inside an encrypted room message. The server sees only the file ID, chunk counts/sizes, ciphertext, and routing metadata.

The upload state machine is:

```text
absent -> pending manifest -> chunks recorded -> ready
```

The client derives deterministic per-chunk nonces and remembers a small plaintext digest guard for every chunk it has encrypted. A retry reuses the already-encrypted bytes for that request; a later re-encryption of the same plaintext is byte-identical, while changed plaintext for the same nonce is rejected locally. Each upload includes a SHA-256 ciphertext digest. The Durable Object accepts an identical retry and rejects a conflicting chunk.

R2 and Durable Object SQLite do not provide a cross-service transaction. The flow is therefore intentionally recoverable:

1. authorize the logical chunk in the Durable Object;
2. conditionally create the R2 object;
3. recover an existing identical R2 object after a prior partial attempt;
4. record its metadata in SQLite;
5. remove a newly created object if the SQLite transition is rejected.

A file becomes downloadable only after every chunk is recorded and the declared encrypted total matches. Downloads stream ciphertext from R2 through the Worker. The browser decrypts each chunk and builds a local Blob. Images, PDFs, MP4 videos, plain text, modern Word `.docx` files, and Excel `.xlsx` workbooks render from that browser-local plaintext. Before DOCX rendering, a dedicated browser worker enforces archive entry, file size, declared expansion, and actual streamed expansion limits. The bundled docx-preview renderer then reconstructs page dimensions, typography, spacing, headers, footers, lists, tables, images, and embedded fonts inside an isolated shadow tree. Active altChunks are disabled, external resources are removed, and unsafe links are neutralized. XLSX workbooks are independently parsed in a dedicated browser worker with bounded archive, XML, sheet, row, column, cell, style, and shared-string limits. The renderer exposes cached cell values in a local, inert table and does not execute formulas, macros, links, or embedded objects. PDF.js supplies the selectable text layer for digital PDFs. Images and scanned PDF pages are rasterized locally and sent only to a dedicated browser Web Worker, where bundled PP-OCRv5 detection and multilingual recognition models run through ONNX Runtime WebAssembly. Recognized text and coordinates remain in active-tab memory and are discarded with the preview or worker.

Optional, explicit PDF handoffs can transfer the selected decrypted PDF bytes and filename directly to a new `https://heron.tools` tab. The user chooses either PDF Rotate & Deskew for scan-angle correction or PDF Workspace for visual page arrangement, rotation, deletion, and export. The handoff does not pass through SecretGram servers, Durable Objects, or R2, but it deliberately expands the endpoint trust boundary to code served by Heron Tools. The source validates the exact popup window, fixed origin, selected fixed tool path, protocol version, and one-time fragment token before transferring the `ArrayBuffer`.

## Retention and cleanup

Read paths reject a room immediately when its stored expiration timestamp has passed. They do not rely on an alarm firing exactly on time.

Message history queries logically exclude messages older than `MESSAGE_RETENTION_SECONDS`. Physical message deletion and abandoned-upload cleanup run through an hourly maintenance alarm. A short-lived room schedules its alarm directly at expiration.

At room expiration, the Durable Object:

1. closes active WebSockets;
2. deletes encrypted R2 objects under the room prefix;
3. deletes SQLite storage.

If R2 cleanup fails, the expired room remains logically inaccessible and schedules another cleanup attempt. An R2 lifecycle rule should provide independent defense-in-depth deletion for orphaned ciphertext.

## Rate limits

A source-scoped rate limiter hashes `CF-Connecting-IP` and routes it to a dedicated rate-limit Durable Object. Fixed windows limit room creation, room access/history, ticket issuance, WebSocket connection attempts, message requests, and file operations.

The Room Durable Object also limits stored messages per claimed device identifier. Device identifiers are ephemeral client-generated UUIDs and are not authenticated identities, so this second layer is flood control rather than an anti-abuse identity system.

## Data intentionally visible to the service

The service can observe at least:

- source IP and Cloudflare request metadata;
- request and connection timestamps;
- room locator and expiration;
- ciphertext sizes and message ordering;
- file IDs, encrypted chunk sizes/counts, and R2 object timing;
- connection/session count per room;
- operational error categories and request IDs.

The service cannot promise traffic-analysis resistance or anonymity.

## Why D1 is not in the data path

Room operations require per-room serialization, WebSockets, alarms, and strongly consistent local state. A Durable Object is the natural coordination atom. D1 would add cross-service consistency work without improving the current room data path.

D1 may be appropriate later for an enterprise control plane containing organizations, SSO mappings, policies, billing, non-content audit events, or room-directory metadata. Such a control plane must not receive plaintext content unless the trust model is deliberately changed.
